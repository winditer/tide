## 简介

工作流编排系统是一个基于 FastAPI 和 Next.js 构建的可视化工作流管理系统，支持多 Agent 协作的有向无环图(DAG)工作流编排。系统允许用户通过图形界面设计复杂的工作流程，集成多种 AI Agent 执行器，并提供完整的运行监控和审批机制。

该系统的核心特性包括：
- 可视化工作流设计器
- 多 Agent 执行支持（Codex、Claude、Qoder）
- 实时运行监控和状态跟踪
- 审批流程集成
- 任务队列和并发控制
- 数据持久化和历史记录

## 详细组件分析

### 工作流节点类型

系统支持多种节点类型的可视化工作流设计。节点类型既被 [WorkflowEngine](file://backend/services/workflow_engine.py) 的一次性 DAG 执行使用（`workflow_runs` / `workflow_node_runs`），也被 [WorkItemService](file://backend/services/work_item_service.py) 的工作项流转引擎使用（`work_items` / `work_item_transitions`）。其中 `stage` / `agent` / `approval` / `delay` 属于「可见节点」（`VISIBLE_NODE_TYPES`），可作为看板列出现；`end` 在看板渲染时也会作为列纳入。

| 节点类型 | 功能描述 | 关键配置参数 (`node.data`) |
|----------|----------|----------|
| start | 开始节点（每个工作流必须有且无入边） | 无 |
| end | 结束节点（必须有且无出边） | 无 |
| stage | 阶段节点 — 工作项停留阶段 / 看板列 | label |
| agent | Agent 执行节点 — 自动创建 Task 并跑 CLI | agentId / agent_id, model, promptTemplate / prompt, cwd, onFailure |
| approval | 人工审批节点 — 暂停等待审批 | label, reason |
| condition | 条件分支节点 — 评估条件选择下一条边 | conditions[ {field, operator, value, targetEdge} ], 边的 `data.isDefault` 或 label = `default`/`否`/`else` |
| delay | 延时节点 — `asyncio.sleep` 后自动推进 | seconds |
| parallel | 并行网关（fork） | 无 |
| parallel_join | 并行汇聚（等待所有上游完成） | 无 |

下面对任务要求覆盖的 5 种核心节点类型，分别说明定义、配置、执行行为以及与工作项/看板的关系。

#### stage：阶段节点

- **定义和用途**：表示工作项停留的「阶段」，是看板可见列的最基本类型。仅作为状态标签使用，不绑定任何自动化动作。
- **配置参数**：`data.label` 用于看板列标题（缺省回退为 `data.name` 或节点 ID）。
- **执行行为**：
  - 在 `WorkflowEngine`（一次性 DAG 执行）中，`stage` 节点被显式跳过：`_execute_node` 直接将其置为 `completed`（output=`stage:skipped`），并立即触发下游节点 ([workflow_engine.py#L290-L296](file://backend/services/workflow_engine.py#L290-L296))。
  - 在 `WorkItemService`（工作项流转）中，进入 `stage` 节点后**不触发任何自动化**——`transition_work_item` 仅更新 `work_items.current_node_id`、记录一条 `work_item_transitions`，等待下一次手动或外部触发的流转。
- **与工作项/看板的关系**：属于 `VISIBLE_NODE_TYPES`，会作为看板列出现；进入此节点的工作项会停在该列，直到被人工拖拽或外部规则推进。

#### agent：Agent 执行节点

- **定义和用途**：自动调用 Agent CLI（Codex / Claude / Qoder 等）完成具体工作的节点，是工作流真正产出动作的核心节点。
- **配置参数**（`node.data`）：
  - `agentId` 或 `agent_id`：Agent 适配器 ID（默认 `codex`）；
  - `model`：可选的模型名；
  - `promptTemplate` 或 `prompt`：支持 `{{path.to.value}}` 模板语法，引用 `context` 中的上游节点输出，或工作项的 `title` / `description` / `priority` / `assignee` / `tags`；
  - `cwd`：执行目录；工作项流转时若节点未配置则回退到项目路径，再回退到当前工作目录；
  - `onFailure`：失败策略，`abort`（默认）或 `continue`。
- **执行行为**：
  - 在 DAG 执行中（[`_execute_agent_node`](file://backend/services/workflow_engine.py#L312-L372)）：渲染 prompt → 在 `tasks` 表插入一条记录，并把 `workflow_run_id` / `workflow_node_id` 关联回 `workflow_node_runs.task_id` → 异步通过 [`agent_executor.run_task`](file://backend/runtime/executor.py) 以 `full_auto=True` 启动 CLI → 流式收集 `output` / `tool_output` / `progress` / `completed` / `failed` 事件 → 在 `_real_agent_execution` 末尾调用 `_finalize_task` 与 `on_task_completed` / `on_task_failed`。
  - 在工作项流转中（[`_trigger_agent_node`](file://backend/services/work_item_service.py#L602-L699)）：通过 `task_service.create_task` 创建任务，把 `task_id` 回写到最近一条 `work_item_transitions`；任务终态由事件驱动 `on_work_item_task_completed` 处理，并以 `_wait_and_record_output` 轮询作为兜底，最终把输出写入 `work_item_transitions.output` 并自动推进到首个下游节点。
  - 失败处理：CLI 不存在或返回失败时，`on_task_failed` 会按节点的 `onFailure` 选择终止 `run` 或继续；工作项流转模式下任务失败/取消同样视为「已结束」并触发推进，由后续节点决定如何处理。
- **与工作项/看板的关系**：属于可见节点，会作为看板列出现。工作项进入该列后异步触发 Agent；任务完成后自动从该列流转到下一个下游列。

#### approval：审批节点

- **定义和用途**：暂停流程，等待人工审批通过后再继续，用于上线前确认、敏感操作放行等。
- **配置参数**（`node.data`）：
  - `label`：用于审批描述（DAG 模式作为 `reason`）；
  - `reason`：工作项流转模式下的审批原因，缺省时回退为 `Work item approval: {title}`。
- **执行行为**：
  - 在 DAG 执行中（[`_execute_node` 的 approval 分支](file://backend/services/workflow_engine.py#L244-L253)）：节点状态置为 `waiting_approval`，通过 `event_emitter.emit_approval_requested` 广播一条审批请求（`approval_id = f"{run_id}:{node_id}"`），随后**阻塞等待**外部回调 [`on_approval_resolved`](file://backend/services/workflow_engine.py#L569-L588)。批准则节点 `completed`、合并 `{output:'approved', reason}` 到 `context` 并推进；拒绝则 `failed` 并按 `onFailure` 处理。
  - 在工作项流转中（[`_trigger_approval_node`](file://backend/services/work_item_service.py#L701-L731)）：调用 `approval_service.create_approval` 在 `approvals` 表写入一条 `type='work_item_transition'` 记录，`detail` 中保存 `work_item_id` 与 `node_id`。审批结果通过 [`on_work_item_approval_resolved`](file://backend/services/work_item_service.py#L951-L1002) 接收：通过则推进到首个下游节点；拒绝则停留在当前节点，不再自动前进。
  - 完成条件：必须收到外部审批结果（API 端点 `…/runs/{run_id}/nodes/{node_id}/approve|reject` 或工作项审批回调），节点不会自行超时。
- **与工作项/看板的关系**：属于可见节点，会形成审批甬道列；该列上的工作项处于「待审批」状态，依赖人工操作才能流转。

#### delay：延时节点

- **定义和用途**：在工作流中插入一段固定等待时间，用于节流、延后执行、留出冷却窗口等场景。
- **配置参数**：`data.seconds`（浮点数，单位秒；缺省为 `1`）。
- **执行行为**：
  - 在 DAG 执行中（[`_execute_node` 的 delay 分支](file://backend/services/workflow_engine.py#L281-L288)）：执行 `await asyncio.sleep(max(0.0, seconds))` → 节点 `completed`（output=`slept Ns`）→ 触发下游节点。
  - 在工作项流转中（[`_handle_delay_node`](file://backend/services/work_item_service.py#L795-L819)）：同样 `asyncio.sleep` 后调用 `transition_work_item` 推进到 `_get_downstream_nodes` 返回的第一个下游节点，`trigger_type='delay'`、`operator='system'`。
  - 完成条件：等待时长到达；进程重启会丢失内存中的 sleep（无持久化恢复机制），需注意不要配置过长的延时。
- **与工作项/看板的关系**：属于可见节点，会作为看板列出现，但工作项停留时间通常很短，仅用于「定时通过」的甬道。

#### condition：条件节点

- **定义和用途**：根据预定义的条件表达式选择一条出边，从而实现分支路由（如优先级路由、标签分流）。
- **配置参数**：
  - `data.conditions`：表达式数组，元素结构为 `{ field, operator, value, targetEdge }`；
  - 支持的 `operator`：`eq` / `neq` / `contains` / `gt` / `lt`（见 [`_compare`](file://backend/services/workflow_engine.py#L865-L880)）；
  - 出边可在 `edge.data.isDefault = true`，或 `edge.label` 为 `default` / `否` / `else` 时，被识别为兜底分支。
- **执行行为**：
  - 在 DAG 执行中（[`_execute_condition_node`](file://backend/services/workflow_engine.py#L475-L506)）：按顺序评估 conditions，命中则取其 `targetEdge`；未命中再尝试默认边；仍未命中则回退到第一条出边；最后把节点置为 `completed`（output=`chose:<edgeId>` 或 `no-edge-matched`）并仅触发被选中的下游分支。
  - 在工作项流转中（[`_handle_condition_node`](file://backend/services/work_item_service.py#L733-L793)）：构造一个仅含工作项字段（`title` / `description` / `priority` / `assignee` / `tags`）的 `context`，按相同规则选边后，递归调用 `transition_work_item` 推进到目标节点，`trigger_type='condition'`。
  - 完成条件：选择并触发一条下游边即视为完成，节点本身不会停留。
- **与工作项/看板的关系**：**不属于可见节点**，不会出现在看板列上；工作项「途经」此节点时只会被瞬时跳过，最终停在被选中分支上的下一个可见节点。

> 说明：`parallel` / `parallel_join` 仅在 `WorkflowEngine` 中实现 fork/join 语义（`parallel_join` 通过 [`_check_all_upstream_complete`](file://backend/services/workflow_engine.py#L731-L757) 等待所有上游 `completed`），工作项流转引擎当前未对其单独建模，按未知节点类型处理。

## 故障排除指南

### 常见问题及解决方案

**Agent CLI 未找到**
- 检查环境变量 PATH 中是否包含 Agent CLI 可执行文件
- 验证 Agent 配置是否正确
- 确认 Agent CLI 版本兼容性

**工作流 DAG 校验失败**
- 确保工作流包含起始节点和结束节点
- 检查节点连接关系，避免循环依赖
- 验证条件节点的条件表达式语法

**审批流程异常**
- 检查审批人配置是否正确
- 验证审批策略设置
- 确认审批通知渠道正常

**数据库连接问题**
- 检查数据库配置和连接字符串
- 验证数据库服务状态
- 查看数据库权限设置
