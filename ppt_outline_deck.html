01 / Title

Lark-Codex Bridge

把飞书 / Lark 群聊变成 Codex 的远程工程操作台。

用户在 Lark 里发起任务，本地运行 Codex CLI，并把进度、结果、审批和项目状态回写到 Lark 卡片。

02 / Idea

让 Lark 成为 Codex 的远程入口

Codex 留在本地工程环境里执行，Lark 承担远程可见、可审批、可协作的控制台角色。

本地执行

保留代码、凭据、Git 状态和 Codex session，不迁移开发环境。

协作入口

下发指令、看进度、批权限、收结果，都在团队日常沟通界面里完成。

低摩擦

不替代 Codex，不重做完整 agent 平台，只增加 Lark 控制层。

工程导向

聚焦修复、检查、写文档、并行拆分和状态追踪。

03 / Problem

本地执行与协作入口割裂

Codex 很适合工程执行，但结果跟踪、审批、多人可见性仍常回到终端和本机客户端。

长任务不可见

  • 进度和结果需要回到本机查看。
  • 审批或失败重试不容易及时处理。

任务容易串

  • 多个任务同时推进时，状态和结果容易混在一起。
  • 不同 session、项目和普通对话缺少统一入口。
04 / Positioning

不是通用 Agent 平台

Lark-Codex bridge 是一个本地运行的 Lark WebSocket 客户端，面向 Codex CLI 和工程任务远程控制。

Codex CLI first Lark cards Local workspace Task approval Project sessions Plan parallelism
05 / Architecture

Lark WebSocket + Python Bridge + Codex CLI

一个轻量脚本把 Lark 事件、卡片更新和 Codex 子进程串起来。

Lark群聊指令、卡片按钮、审批动作。
WebSocket接收消息、按钮回调和消息事件。
Bridge解析指令、维护状态、构建卡片。
Codex CLI本地执行任务、写入 session 文件。
Cards回写进度、结果、失败和审批。
06 / Features

主要功能

从指令入口到任务卡、项目面板、Plan 并行和日报统计，覆盖工程执行的基本闭环。

指令入口

自然语言、模型前缀、项目切换、会话创建。

任务卡片

状态、目录、模型、耗时、Session、最新输出。

审批处理

批准或拒绝高风险操作，并按批准后的 sandbox 重试。

会话管理

项目、普通对话、当前项目会话的创建、切换和归档。

Plan 并行

任务清单拆分，多 Codex 子进程并行执行。

日报统计

按日期汇总总指令数、审批、失败、更新和修复。

07 / Traits

关键特性

工程工具需要少打扰、可追踪、可恢复，而不是只展示漂亮结果。

Local本地执行，保留工程上下文。
Visible长任务进度和结果在 Lark 可见。
Approve权限风险在协作界面闭环。
ParallelPlan 模式支持多任务并行。
08 / Plan

Plan 并行模式

把任务清单拆成多个 Codex 子任务，默认使用 Git worktree 和独立分支隔离改动。

输入

  • - 任务、* 任务、待办项。
  • 支持数字编号和同一行数字列表。

执行

  • 一个 PlanRuntime 保存整体计划。
  • 调度线程按并发上限启动子任务。
  • 每个子任务是独立 Codex 子进程。

隔离

  • 每个子任务创建独立 worktree。
  • 每个子任务创建独立分支。

收尾

  • 运行 git diff --check。
  • 有改动进入待提交审批。
  • 当前不自动合并主分支。
09 / Safety

审批与安全

Codex sandbox 和 Lark 审批卡片共同构成风险控制，批准后只对原任务重试。

触发信号

  • sandbox 拒绝。
  • 权限不足。
  • .git/index.lock。
  • permission denied。

处理流程

  • 待审批项显示在对应任务卡中。
  • 点击批准或拒绝。
  • 审批结果回写原卡片。
  • 批准后使用更高权限策略重试。
10 / Reporting

日报和状态

日报不再按“会话次数”理解，而是按用户下发的“总指令数”统计。

/status项目、目录、运行状态、会话和任务概览。
/daily当天进展日报。
date支持指定历史日期。
count总指令数、审批总数、失败总数。

12 / Boundaries

当前边界

边界说清楚，后续路线才不会变成泛化平台改造。

状态持久化

脚本重启后，部分运行态仍需要依赖 session 文件或日志恢复。

Plan 收尾

当前不会自动合并主分支，worktree 清理和 cherry-pick 仍需增强。

多用户部署

多人共享同一应用凭据会带来事件路由和权限问题。

统计口径

日报已修正总指令数，但历史审批和失败仍可继续增强持久化。

13 / Roadmap

后续规划

短期继续修统计和面板，中期补齐 Plan 收尾与状态持久化，长期走向中心化多用户服务。

短期

  • 完善历史日报、审批和失败口径。
  • 强化当前对话和最近指令展示。
  • 补充解析和统计测试。

中期

  • Plan 合并、cherry-pick 和清理。
  • 运行态持久化。
  • 卡片回调增加文本 fallback。

长期

  • 多用户权限与路由。
  • 中心化 bridge 服务。
  • 联动 Lark 文档、审批、任务、日历。
14 / Closing

做窄，把工程流打通

Lark-Codex 不追求成为完整 agent 平台，而是把 Lark + Codex 的工程执行闭环打通。

最有价值的方向：在协作入口里稳定地下发、跟踪、审批和收敛 Codex 工程任务。
